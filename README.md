# paper-to-toy — 紙で試すための型紙（papercraft）のエンジン

型紙（papercraft）を作るエンジン。江戸の玩具を紙で試すために、寸法から型紙の PDF を作り、刷れる・組めるかを機械で検査する。**Built with Claude: Japan 2026（ハッカソン）で作っている。**

A papercraft template engine: generates printable PDF patterns from dimensions and checks them before and after rendering. Being built at Built with Claude: Japan 2026 (hackathon).

## 提出物との関係

このエンジンは [utsushi](https://github.com/akihidem/utsushi)（ハッカソンの提出物）の一部を、開発期間中（2026-11-02 12:00 JST 以降）に切り出した物です。コードはすべて期間中に utsushi の repo で新しく作りました。提出物は utsushi で、このエンジンは単独の提出物ではありません。元の commit: utsushi `1d17988`（その後の v8 の直しは utsushi `74c354c` から写した）。

## 何をするか

型紙は正解ではなく、AI が考えた仮説です（どの紙にもそう刷る）。作って、動きを確かめて、直していきます。作り方を決めた本人の言葉は [docs/philosophy.md](docs/philosophy.md) にそのまま残しています。


```
寸法（JSON） → 配置 → 描く前の検査 → SVG / PDF → 刷った後の検査 → PNG
```

- **描く前の検査**: 寸法の範囲、部品と文字が印字域に収まるか、部品どうし・文字どうしの重なり（文字の幅はフォントから測る）、部品表の素材と刷る部品が全部載っているか、描き直しの絵が折り線と糊代をまたがないか、穴が部品の中にあるか、雛形ごとの物理（扇が筒に収まるか・押し切れるか・像の足が台に貼れるか・重心が軸より下か など）。
- **刷った後の検査**: できた PDF から pdftotext で、所蔵の文・永続 ID・改変の注記・出典 ID・仮説の文が、そのまま読み直せるか。貼られた画像が 0 枚か（原図を貼らず描き直す）。
- 検査に落ちた紙は正しい名前で残さない（刷った後の検査で落ちた紙は `*.rejected.pdf` だけにし、描く前の検査で落ちた時は同じ名前の前の回の紙も消す）。検査できない（exit 4）時は、前の回の紙に触らない。

雛形は、提出物（utsushi）と同じ 2 つと、『江都二色』のほかの玩具の雛形（下の 2 つ目の表）。

| 雛形 | 玩具 | 仕組み | 刷る形の寸法（必ず書く） |
|---|---|---|---|
| `slider_fan` | 御来迎 | 角筒の中で動く台に蛇腹の扇と像を載せ、押し上げると開く。扇の中心の置き方も描き分ける（`hub`: `axle` 軸・`rim` 口の台。既定 `axle`） | `push_part`: `tab` つまみ・`tube` 内筒・`stick` 棒 |
| `pivot_counterweight` | 張子の首振り虎 | 箱の胴に軸を通し、重りで頭を揺らす | `mount`: `neck` 首・`hang` 吊る |

刷る形の寸法は仮説の違いそのもの（どれが昔の作り方かは分からない）なので、既定の値に頼らず必ず書く。

どの寸法も計算と検査で出した値です。検査は「刷れる・形の上で組める」事を見る物で、紙で動く事の保証や、昔の作り方の証明ではありません。

## 使い方

Python のパッケージ名は `omochae`（元の repo と同じ名前のまま）。

要る物: Python 3.11 以上、[uv](https://docs.astral.sh/uv/)、poppler-utils（`pdftotext`・`pdfimages`・`pdftoppm`）、fontconfig（`fc-match`・`fc-list`）、字 Noto Serif CJK JP。

Ubuntu 24.04 では、まっさらな環境からこれで揃う（Docker の `ubuntu:24.04` で確かめた）:

```bash
sudo apt-get install -y python3 pipx poppler-utils fontconfig fonts-noto-cjk
pipx install uv   # uv の入れ方は https://docs.astral.sh/uv/ の物でもよい
export PATH="$HOME/.local/bin:$PATH"   # pipx が uv を置く所
```


```bash
./init.sh     # .venv を作り、依存を入れる。足りない物があれば名指しして exit 4
./run.sh      # 凍結した場面と試験を全部回す。結果は out/RESULT.md
```

最小の例（型紙を 1 枚刷る）:

```bash
PYTHONPATH=src .venv/bin/python -m omochae --scenario examples/fan_tab.json --out out/fan_tab
# → out/fan_tab.svg / .pdf / .png
```

`examples/fan_tab.json`:

```json
{
  "template": "slider_fan",
  "source_id": "NDL-1187053-R0000005-L",
  "params": {"push_part": "tab"},
  "inject": {}
}
```

寸法の JSON を直に渡す時は `--params`（`--template` で雛形を選ぶ。出典は雛形ごとに既定がある）:

```bash
echo '{"mount": "hang", "axle_height": 50}' > tiger.json
PYTHONPATH=src .venv/bin/python -m omochae --template pivot_counterweight --params tiger.json --out out/tiger
```

引数の説明は `python -m omochae --help`。

`params` に書かなかった寸法は雛形の既定値（`DEFAULTS`）を使う。変えてよい名前と範囲は雛形の `RANGES`。`source_id` は `data/sources/` の出典の記録の名前で、型紙に刷る所蔵と改変の印をここから取る。

描かずに検査だけを回す時は Python から:

```python
from omochae.compose import check_params
import json
source = json.load(open("data/sources/NDL-1187053-R0000005-L.json", encoding="utf-8"))
print(check_params("slider_fan", {"push_part": "tab", "fold_count": 40}, source))
# {'passed': False, 'errors': [
#     'FAIL F5.fan_clearance [蛇腹の扇] 帯の長さでは 406° 開くが、筒の口の角に当たって 289° までしか開けない',
#     'FAIL F5.print_area [蛇腹の扇] 印字域の外に出ている (127.0, 36.2, 200.0, 376.2)',
#     'FAIL F5.text_overlap [糊代] 文字が部品「蛇腹の扇」と重なっている',
# ]}
```

## 分かっている事

- つまみで動かす形（`push_part: tab`）は、溝を筒の下の端まで開いた切り込みにしてある（くり抜くより切りやすいため）。溝の下に止めが無いので、内筒は手で支えて押す。紙の摩擦で止まるかは実物で確かめていない。
- 検査は寸法と配置と印を見る物で、紙の厚さや糊の効きなど、実物の手触りは見ない。
- 虎の吊る形（`pivot_counterweight`・`mount: hang`）では、軸の穴は耳の位置で決まり、`axle_height` は型紙に効かない（変えても型紙は変わらない）。一方で、重りが底に当たるかの検査は `axle_height` で見ている。重りの位置（`weight_below_axle`・`weight_behind`）も検査の見込みにだけ使い、型紙には「あごの近く」としか刷らない。
- 同じ吊る形で、軸の穴から頭の上までを式では 8mm と見込んでいる。前提は、頭を帯の下の端に 4mm 重ねて貼る事（型紙の帯は長さ 18mm・穴は端から 6mm なので、重ねずに貼ると 12mm になり、式の見込みと合わない）。
- `spinner`:
  - 値はどれも実物で確かめていない見込み。指で回す速さ 60rad/s、紙と竹串の密度がそれ。
  - 紙のたわみ・空気の抵抗・先の摩擦・円盤の反りは式に入れていない。
  - 四角の羽の傾きの式は、羽を 2 つの穴で支える前提。座金は別の部品なので、実物ではもっと傾きうる。
  - 銭独楽の円錐は、先を切った円錐台。式は全高で見ている。
  - 紙の風車は、14 左の「十字の棒に 8 枚羽の輪が 2 つ」を、1 枚の紙の風車に置き換えた翻案。
- `whistle`:
  - 鳴る窓・歌口の比・紙の硬さは見込み。どれも実物で鳴らしていない。
  - 舌の式は、空気の重さと減衰を入れていない。
  - 鈴の形は、糸の長さが竹筒の間に届くかを見ていない。
  - 形に関わらない寸法を渡しても、黙って受ける。
- `popup_jar`:
  - 紙と紙の摩擦 0.5・紙の厚さ・穴の遊び・隠れる余り 2mm は見込み。
  - 押し帯の座屈は式にしていない。
  - 静かな時は帯が箱の底から出るので、手で持つ。
  - 壺の丸い形は角筒に替えた。
  - 静かな時の足と糊代の干渉では、帯が上の穴の中で横へ寄る分を入れていない。
- `slide_box`:
  - 何が滑るかは図から決まらない。どちらの形も 1 つの翻案。
  - 止めと仕切りは図にはっきりと見えない。抜けないように足した物。
  - 中箱の形（sleeve）の組み上がりの絵は、仕切りと鼠を閉じた位置で描く（引き出した時の位置ではない）。
- `wheel_cart`:
  - 質量と厚みは見込み。重心は前後の向きだけで見る。
  - ぶりぶりを車と読んだのは、一般の説明による推定。
  - 春駒・ぶりぶりの中の四角い穴はカッターで切る（大人）。
  - 春駒の割り箸を止める印は、差し込みが 0.5mm 以下だと刷らない（折り目で止める）。0.5mm のすぐ上では、印が折り目の破線から 0.3mm ほどしか離れない。
  - 柄を差す深さの下限 2mm は見込み。
- 寸法を変えた向きを式で数え直す `omochae.metrics`（元の repo の F7 の道具）は、御来迎と虎の雛形だけを知っている。ほかの族の雛形で呼ぶと KeyError になる（この repo の中では呼ぶ所が無い）。
- `balance`:
  - 密度・竹串の重さ・余裕の量は見込み。紙の曲がり・糊の重さ・摩擦は入れていない。
  - 弥次郎兵衛は、表も裏も刷った面を上にして、裏返さずに重ねる。外から見える裏の面は無地になる。
  - 左右の粘土の差の傾きは、左に足した時だけで見ている。
  - 机との余裕に、竹串を立てる粘土の山の高さを入れていない。
  - 起き上がり小法師の底の帯は、まっすぐな紙なので、すぼまる円錐の内には平らに沿わない。
- `twist_drum`:
  - 玉は結び目の高さの水平面を回ると見ている。重力・糸のたるみ・跳ね返りは入れていない。
  - 「縁は鳴りが鈍い」・竹串の太さ・紙の厚みは見込み。
  - 諫鼓の仕組みはどれも推定。引く棒の切り欠きは、刷る留め具に置き換えた。
  - 諫鼓の回る数は、棒を引いた長さをそのまま糸の出る長さと見るので、多めに出る。糸の穴は軸の真横から始まるので、既定では式と組み方の文が約 1.8 回、数え直すと約 1.3 回。
  - 諫鼓は、留め具が南の壁のどこで止まるかを決めていない（印が留め具のどちらの端か）。留め具の旗が軸の竹串に当たりうる。
  - 竹串の尖った先の扱い（切り落とす・大人がする）を、組み方に書いていない。
  - 3 つの形が 1 つの寸法の組を分けて使う。形に関わらない寸法を渡しても、黙って受ける。
- `float`:
  - 水 1g/cm³・紙 150g/m²・テープ 60g/m²・油粘土 1.7g/cm³ と、乾舷 5mm・ふちが水に着く傾き 12°・GM 3mm の下限は見込み。どれも実物で浮かべていない。
  - 式は吸水を入れない（乾いた紙の重さと形のまま見る）。外側をテープかろうで覆うのはそのため。濡れた後の浮き方は確かめていない。
  - 戻りは小さな傾きの式（GM）で、狭い向きの横揺れだけ見る。大きく傾いた時の戻りを見るのは、風受けつきの息の検査だけ。糊の重さ・葉の厚みは入れていない。
  - 紙の舟・水よけ・粘土の重り・風受けは昔の物に無い翻案。図では葉が直に浮き、何で浮いていたかは分からない。
  - 風受けは、壁の上に出る事・底に収まる事・息で倒れない事を見る。息で倒れないかは、息が舟を傾ける腕（余裕 2 倍）が、箱の断面で出した舟が戻す腕の最大に届かない事で見る。息の速さ 4m/s と抗力係数（口の側 1.4・丸い側 0.7）は見込みで、実物で量っていない。舟の壁と人形が受ける息・回る速さ・水の抵抗は式にしていない。
  - 風受けの山折りの線は、歯ごとでなく幅いっぱいの 1 本で刷る（歯ごとに刷ると実線に見える）。左の端の歯だけは線が切れずに見える。折りの書き出し（foldsim）では、この線が歯の間の切り込みをまたぐ（Origami Simulator では確かめていない）。
  - 風受けの無い形は、水をかき回した渦に舟を乗せて回す（図の渦の線の解釈）。かき回す 5 回は見込みで、渦の速さと舟の回り方は式にしていない。
  - 舟は全部を谷折りにして刷った面を内にする（底の貼る所の印が内に要るため）。雷文は壁の内側に出て、壁の外側は紙の白のまま。
  - 組み方の文は、サイトの手順の紙（A4）に収まるよう 16 行までに詰めてある。手順ごとの直しの行き先（`step_targets`）は、作った人の報告（Issue #21）の手順の番号から寸法と見込みの値を引くための表で、報告の集計からはまだ呼んでいない。
  - 式は人形が葉（舟）の真ん中に立ち、粘土が四隅の四角に同じ重さずつ載ると見る。その所の印を刷るが、ずらして貼ると式と違う物になる。
  - 形に関わらない寸法（`none` の形の `cup_width` など）を渡しても、黙って受ける。
  - 人形は舟の幅の向き（刷った矢印と直角）に立てる。向きの刻みを刷る所（1mm）が無い寸法は落とす。風受けの無い形にもこの床が掛かるので、葉の上限が 1mm ほど狭い。
- 位置の印の形（赤茶の点の線）に移したのは、エンジンの側と `wheel_cart`（鼠車の人形を貼る所・春駒の割り箸を止める所）。ほかの族の雛形は、まだそれぞれの色と線で印を描く物がある。
- 位置の印は、色（赤茶）と点の線で見分ける。白黒で刷ると色は使えず、点の線と凡例だけが手がかりになる（刷って確かめていない）。
- `pull_nod`:
  - 摩擦係数 0.4・紙の重さ・粘土の密度 1.8・「摩擦の 3 倍」の余裕・2 羽の面の間 3mm は見込み。紙のたわみと糸の擦れは入れていない。
  - 藁苞の鶏の底の糸の穴は、上の面と左右が逆になっている（糸が苞の中で斜めに走る）。
  - 振り獅子の顎の粘土の玉と、米搗き人形の尾の粘土の玉は、大きいと頭や柱に当たる。それを見ていない。
  - 米搗き人形の台の糸の穴が、臼の真下に来る寸法を落とさない。
- `lever_link`:
  - 割ピンの頭の大きさ・穴の余白・紙の厚さ・指先の大きさ（半径 8mm）・机との余り 2mm・穴の許し ±0.2mm は見込み。
  - 当たりは、回る部品と割ピンの頭・机・持つ所の間だけで見る。紙の層どうしは当たらないと見る。
  - 相撲は B の立つ足を指で押さえる前提。からくり台は、厚紙に貼った門の枠を机に立てて押さえる前提（要る厚紙の厚さは確かめていない）。
  - 厚紙に貼る部品を粗く切る余白は 2mm（部品の間 4mm の半分）。4mm まで広く切ると隣の部品に届く。竿登りの猿は隣の部品がもっと遠く、文の「間の半分」は当たらない。
- `launcher`（飛ばす玩具。子どもは大人と一緒に使う）:
  - ためる力の上限 30mJ は、この雛形が選んだ余裕の値。規格の値ではない。0.08J はよく言われる目安だが、出所を確かめていない。
  - 紙の硬さ（縦弾性係数 6GPa を硬い側の見込みに使う）・握りの幅 55mm・糸のたるみ・紙の玉のかさの密度の上限 0.25g/cm³ は、どれも見込み。実物で確かめていない。
  - 既定の寸法は上限に近い（紙の厚さで約 3.7%、引きで約 5.6% 増えると越える）。紙の厚さは、刷った止めの条件（重りを下げた時の下がり）で確かめる。条件を満たさない腕は使わない。
  - 引き金の掛け方と外し方、弩の腕の根元の折りの硬さは確かめていない。
  - おはじきやビー玉など硬い物は、形では筒に入るのを止められない。止めているのは組み方の文だけ。
  - 引き金の細い切れ込み（幅 2mm）は外形の一部なので、組み方の文は「部品を実線で切る」に含めている。大人が切るとも、カッターとも言っていない。
<!-- 族の限り -->
- 同じ入力で、同じ版の道具と同じ字の機械なら、PDF はバイトまで同じになる。作った時刻の欄は今の時刻でなく決まった値にしてある（作った時刻は PDF から読めない）。
- 出力の SVG・PDF・PNG は、その回だけの仮の置き場で作って検査してから正しい名前へ移す。ただし 3 つは 1 つずつ移すので、移す途中で止まる（機械が落ちる等）と、新旧が混ざって残りうる。

## 作り方の印（紙一枚・折るだけ・当時の材料）

形ごとに 3 つの印を出す（#53）。どれも優劣の印ではなく、作り方の選択肢を選ぶための物。

```bash
PYTHONPATH=src .venv/bin/python -m omochae.ways          # 一覧
PYTHONPATH=src .venv/bin/python -m omochae.ways --json   # サイトの絞り込みに使う
```

- 紙一枚: A4 1 枚に刷った紙だけで作れる。糊・はさみ・定規・カッターなどの道具は使ってよい（本人の言葉「一枚の紙から作る選択肢もある」）。
- 折るだけ: 1 枚の紙を切らずに折るだけで作る。今の雛形には無い。
- 当時の材料: 紙のほかの材料が、江戸の頃にもあった物（竹・糸・粘土・木）だけ（本人の言葉「竹とか糸は江戸時代にもあったし使ったらよく再現できるということ」）。今の物で代えた材料（テープ・割ピン・ビーズ・厚紙など）は、一覧に出す。
- 本人の決定で「紙一枚」と「折るだけ」は別の印で持つ。印は雛形に宣言させず、部品表・用意する物・部品から出す。

## 折れる様子を Origami Simulator で見る

型紙の折りのある部品を、[Origami Simulator](https://origamisimulator.org)（ブラウザーで折り線図を折って見せる道具）が読める SVG に書き出す。入口は型紙と同じ（`--scenario`、または `--template` と `--params`）で、書き出す前に型紙と同じ検査を通す（落ちれば 3）。

```bash
PYTHONPATH=src .venv/bin/python -m omochae.foldsim --scenario examples/fan_tab.json --out out/foldsim
# → out/foldsim/slider_fan_tube_foldsim.svg ・ _pusher_ ・ _base_ ・ _fan_（部品ごとに 1 つ）
```

書いた SVG を Origami Simulator の「File → Import」で開く。線の色は Origami Simulator の約束に合わせた（外形と中を切り抜く穴 黒 `#000000`・山折り 赤 `#ff0000`・谷折り 青 `#0000ff`）。検査に落ちた時と、書き出した時は、前の回の同じ頭の SVG を残さない（`--parts` で部品を減らした回は、その部品だけになる）。線の濃さは付けないので、どの折りも折り切った角度（180°）として扱われる。紙の厚みと摩擦は模擬しないので、実物の動きとは違う。部品を選ぶ時は `--parts fan,tube`。

## エンジンごとの改善の輪（作る過程の記録 → 直しの案 → 人の採否 → 次の版）

型紙 1 枚の直し（寸法を 1 つ変えた次の版）とは別に、雛形から刷る全部の紙に効く直しを、作る過程の記録から起こす（Issue #63・#65・#68）。
機械は材料を束ねるだけで、採るかどうかも、直した後にどうなったかも決めない。

```sh
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop check examples/bundles/sample_made_up.json   # 束の形と連絡先の形（0 通る / 3 落ちる）
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop take examples/bundles/sample_made_up.json    # 入口。連絡先の形のある文は落として数だけ残す
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop propose                  # 直しの案（下書き）を起こす
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop list                     # 案の一覧（show <番号> で当たった文つき）
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop adopt EP-0001 --by <人>   # 人が採る（reject で採らない）
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop release --commit <番号> --by <人> --sheet-set slider_fan=<組の名>   # 直しが main に入った後、次の版を刻む
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop compare                  # 版ごとの数を並べる（判定はしない）
```

- 束は、サイトの側が作る過程の記録（止まった所・動きの結果・工夫の言葉・感想・質問・話した事）を、雛形の id と刷った組ごとに束ねた JSON 1 つ。欄は決めた物だけで、決まりの外の欄がある束は束ごと断る。名前・連絡先・人の印の値・写真・声・映像・分より細かい時刻は入れない。
- 話した事は、声から字にした物を 3 つの種類で受ける（声そのものは束に無い）: `think` 作る前に仮説を見て話した考え・`craft` 作りながら話した工夫（手順の番号つき）・`keep` できた物を上げた後の話。群の `craft_steps` は、手順ごとの「話した工夫の数と人の数」。報告の欄の案（Issue #62）の `when` とは、idea が think・making が craft・made が keep に当たる。
- 案の行き先は 3 種。
  - 雛形: 同じ手順で止まった人が 2 人から（人の印の無い記録だけなら、止まったの札が 3 回から）。その段で話された工夫も、同じ案に付く。
  - 雛形: 止まったの札が重なっていない段でも、同じ手順で工夫を話した人が 2 人から（人の印の無い記録だけなら 3 件から）。
  - 雛形: 作った人の工夫の言葉（直した点・思いつき・話した工夫・できた後の話）は 1 件から。
  - 部品（雛形をまたぐ共有の所。刷り方・凡例・位置の印など）: 同じ種類の困り事が 2 つ以上の雛形で出た時。
  - 生成の決まり（床と既定の寸法）: 検査を通って刷られた紙で、動かない側の札が 2 件から。「わからない」は動かない側に数えない。作る前の考えは、この案に付く（考えだけでは案にしない）。
- 束の上の段の `current_sets` は、雛形の id ごとの今の刷った組の名（無くてもよい。サイトの側が書く）。記録の紙の組が今の組と違う群から起きた案には、「今の組は ○○。この記録は前の組の紙の物（もう直っているかを、先に見る）」と並ぶ。前の組の記録だからといって、案を捨てはしない（直っていない事もある。決めるのは人）。`compare` では、今の組の行に印が付く。
- 案は数と当たった文だけを持ち、新しい寸法の値を持たない。採否は、人が名前を書いて決める。採った案は「次の版の予定」に入り、4 つの見出しの Issue の下書きが出る（立てるのは人）。
- Issue の下書きは、作った人の言葉（当たった文）を、4 つの見出しの外の「手元の材料」に分けて置く。声から字にした話は、作る側だけが読む約束で残した言葉なので、Issue にはそのまま写さず、人が読んで自分の言葉でまとめる。
- 直しが main に入ったら、人が `release` で次の版を刻む。版の台帳は `data/engine/versions.json`（版の番号・採った案の番号と行き先と題・件数・commit・変わった刷った組）。作った人の文と、決めた人の名前は台帳に入れない。
- `compare` は、雛形ごとに刷った組ごとの数（報告の数・動きの札の数・止まった段の札と人の数・やめた段・最初に動くまでの分の幅・話した事の数）を並べる。上下や割合は出さない。件数が少ないと、差があっても偶然と分けられず、作った人も作り方も版ごとに違うため、読むのは人。
- 分かっている限り:
  - 見本の束 `examples/bundles/sample_made_up.json` は、形を見せるために作った見本で、実の記録ではない。実の記録の束は、サイトの試行の記録 2 件から出した物を通しただけ（群 1 つ・案 1 件。この案は前の組の紙の記録から起きた物で、中身は次の組でもう直っていた）。話した事の入った実の束は、まだ 1 つも通していない。採った案も、刻んだ次の版も、まだ無い（台帳は版 1 だけ）。
  - 話した工夫の案は、同じ段で話した人の数だけを見る。話の中身が同じ事を言っているかは見ない（人が読む）。手順の番号から直す所を引く表（雛形の `step_targets`）は、まだ使っていない。束が雛形の形（form）を持たず、表を持つ雛形も一部だけのため。
  - 名前は形では落とせない。束と案と Issue の下書きは git の外（local の下）にだけ置き、下書きは人が読んでから使う。
  - 文から困り事の種類を拾う所は、語の一致だけの荒い束ね。当たった文を案に付けるので、人が読んで確かめる。
  - 版の印は紙に刷らない（必須 2 種の刷った絵を変えないため）。版と紙は、束の「刷った組」と、`release` で書く刷った組でつなぐ。
  - 入口の床（F13.bundle・F13.pii・F13.proposal・F13.human・F13.version）は、この道具の床。凍結の基準の一覧には、まだ載せていない。
  - 束は、同じ出し元の物は新しい 1 つだけを数える（束はその時までの記録の全部なので）。
